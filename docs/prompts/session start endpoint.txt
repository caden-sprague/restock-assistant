CRITICAL: You are implementing the `POST /session/start` endpoint on the backend
in TypeScript. This endpoint bootstraps the entire restock flow — no session
means no planogram, and every command downstream fails. It **MUST NOT** talk to
Micromart directly and **MUST NOT** read the auth cookie directly.

### READ FIRST — SOURCE OF TRUTH ###
Read `docs/restock_assistant_mvp_plan.md` before writing anything. It is the
spec: follow its folder structure, models, and naming. If anything in this prompt
conflicts with the plan, **flag it and update the plan doc in the same change** —
do not silently implement the deviation and let the two drift apart.

### TASK ###
Build the endpoint the mobile app hits to kick off a restock session: fetch the
planogram, build the in-memory inventory index, and store it as the active
session.

### PROJECT CONVENTIONS ###
- **Node + TypeScript, Fastify.** Fastify appears **only** in `app.ts` and
  `sessionRoutes.ts`. The controller takes a plain input object and returns a
  plain response object — no `req`/`reply` anywhere near it.
- **Constructor injection**, wired up in `app.ts`. Nothing else calls `new` on a
  service.
- **In memory for now** — one user, one active session at a time. No database.

### REQUEST BODY — OPTIONAL, WITH ENV FALLBACK ###
The body may carry `siteId` and/or `restockSessionId`.
- Missing or blank → fall back to the env var defaults.
- **Trim** both values.
- A whitespace-only string is treated as **not provided**.

### WHAT HAPPENS ON START ###
1. Fetch the planogram from Micromart for that site.
2. Build the in-memory inventory index from it.
3. Save the active session: site id, restock session id, the index, and a
   `startedAt` timestamp.

### CRITICAL — LAYERING ###
This endpoint **NEVER** talks to Micromart directly. It goes:

```
SessionController → SessionService → PlanogramService → MicromartClient
```

`MicromartClient` is the **only** module that knows real Micromart URLs and
payloads. Auth comes from the **`AuthProvider` interface** — do not read the
cookie directly anywhere.

### SUCCESS RESPONSE ###
```
{ status: "ready", siteId, restockSessionId, itemCount }
```
`itemCount` is how many items ended up in the index.

### ERROR HANDLING ###
Every response carries a `status`; errors also carry a `code`. Micromart failures
throw a typed `MicromartError` that **already has the right code on it**:

```
expired cookie      → AUTH_EXPIRED
other bad response  → PLANOGRAM_FETCH_FAILED
could not connect   → NETWORK_ERROR
```

- The controller **passes that code straight through**. Do **NOT** string-match
  error messages.
- If something genuinely unexpected blows up (a real bug), **do not** catch it
  and invent a fake code — let it bubble up to the app-level handler.

### PIECES EXPECTED ###
- **`SessionService`** — owns the active session. `startSession(siteId,
  restockSessionId)`, `getActive()`, and `getActiveIndex()` which throws
  `SESSION_NOT_READY` when there is no session yet.
- **`SessionController`** — framework-agnostic handler. Does the env-default
  fallback, calls the service, maps `MicromartError` to the error response.
- **`sessionRoutes.ts`** — thin Fastify wrapper: read the body, call the
  controller, set the HTTP status from the **shared status-mapping helper** (the
  body-to-status mapping lives in one place so all routes agree).

### LOGGING ###
Log around session start and any failures — this is the **dev/diagnostic** log,
kept **separate** from the audit log. **Never log the auth cookie.**

### TESTS ###
Unit-test the controller with a faked `SessionService`:
- Env fallback: empty body, values given, trimming, whitespace-only, only one
  field set.
- The `ready` response includes `itemCount`.
- A `MicromartError` maps to the right code.
- An unexpected error **propagates** instead of getting swallowed.
