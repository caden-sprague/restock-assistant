CRITICAL: You are implementing the command endpoints (`POST /commands` and
`POST /commands/confirm`) on the backend in TypeScript. This is the path that
writes real inventory corrections to Micromart — a wrong order of operations here
submits bad data. The `CommandController` **MUST only orchestrate**: it never
parses, matches, or submits itself.

### TASK ###
Build two endpoints:
- **`POST /commands`** — takes the raw command text and runs the whole flow.
- **`POST /commands/confirm`** — the follow-up after an ambiguous match; takes
  the item id + quantity the user picked.

### PROJECT CONVENTIONS ###
- TypeScript + Fastify. **Fastify only in `app.ts` and `commandRoutes.ts`.**
  Controllers and services stay framework-agnostic.
- Everything injected through constructors and wired up in `app.ts`.
- **The controller only sequences collaborators**, depending on their interfaces,
  not their guts:

```
parse (CommandParser) → resolve (InventoryResolver) → submit (RestockService)
```

### /commands — EXECUTE IN THIS ORDER ###
1. **No active session → `SESSION_NOT_READY`, immediately.** A command means
   nothing without a planogram to resolve against, so check this **first**,
   before anything else happens.
2. **Parse** the text into a `ParsedCommand` (action, productQuery, quantity).
   - Parser throws `ParseError` → return `UNPARSEABLE_COMMAND` with a friendly
     message, e.g. *"Try something like 'set fairlife to 5'"*.
   - Parser throws **anything else** → that's a real bug, **let it propagate**.
3. **Validate the quantity BEFORE resolving** — an ambiguous result must never
   come back carrying a bad quantity. Must be a **non-negative integer**,
   otherwise `INVALID_QUANTITY`.
4. **Resolve** the productQuery against the active index. The resolver is layered
   (exact → alias → contains → fuzzy) and returns one of three things:
   - **nothing found** → `PRODUCT_NOT_FOUND`, and mention what they actually typed.
   - **multiple matches** → return `needs_confirmation` with the options as
     minimal `{ name, siteInventoryId }` refs (**do not leak the full internal
     item to the app**) plus the quantity, and **submit nothing**.
   - **one match** → submit it.
5. **Submit** via `RestockService`, which builds the payload and posts it through
   `MicromartClient`:

```
{ "type": "correct", "quantity": 5, "site_inventory_id": 294450 }
```
   Return whatever it gives back — a success with the item + quantity, or a
   mapped `MicromartError`.

### /commands/confirm ###
Body is `{ siteInventoryId, quantity }` the user picked after a
`needs_confirmation`, so there is no text to parse. **Do not trust it.** Run it
back through the same `RestockService.submit` path so everything is re-checked:
- active session,
- valid quantity,
- the `siteInventoryId` is **actually a real item in the current session's
  planogram** (`PRODUCT_NOT_FOUND` if it is not).

Then submit.

### CONTRACT AND ERROR CODES ###
Every response has a `status` (`success` | `error` | `needs_confirmation`) and
every error has a `code`. Pass `MicromartError` codes **straight through**:

```
AUTH_EXPIRED / MICROMART_POST_FAILED / NETWORK_ERROR
```

Keep **one shared helper** mapping a response body to its HTTP status so all
routes stay consistent.

### REQUEST SCHEMA VALIDATION ###
Add Fastify JSON-schema validation on **both** route bodies so a malformed
request gets a clean 400 instead of exploding inside a handler.
- **Structure only**: `/commands` needs a string `text`; `/commands/confirm`
  needs an integer `siteInventoryId` and a number `quantity`.
- **Reject unknown fields.** **Do not coerce types** — a string `"5"` is not a
  number.
- **Semantic rules stay in the services** — the non-negative-integer check is
  `INVALID_QUANTITY`, a well-formed id that is not in the planogram is
  `PRODUCT_NOT_FOUND`. Do not check the same thing in two places.
- A schema failure returns its own **`INVALID_REQUEST`** code — add it to the
  error codes and the status map.
