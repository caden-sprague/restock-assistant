### CORE WORKFLOW ###
1. A restocker manually starts a restock session at a kiosk.
2. For the MVP, assume the Micromart auth cookie/session, `site_id`, and
   `restock_session_id` are **manually obtained and hardcoded**.
3. The backend uses that hardcoded auth/session to request the planogram:
   ```
   GET https://classic.micromart.com/api/sites/{site_id}/planogram
   ```
4. From the planogram, extract products from `cells[].site_inventory`, especially:
   - `site_inventory.id`
   - `site_inventory.inventory.recipe.name`
   - quantity and any useful metadata
5. The mobile app lets the restocker enter commands like:
   - "set fairlife to 5"
   - "fairlife 5"
   - "correct fairlife 5"
6. The backend parses the command, resolves the product name against the
   planogram, finds the correct `site_inventory_id`, and posts a correction event:
   ```
   POST https://classic.micromart.com/api/restocks/{restock_session_id}/events
   { "type": "correct", "quantity": 5, "site_inventory_id": 294450 }
   ```
7. If the product name is **ambiguous** (e.g. multiple Fairlife products), the
   backend returns a clarification response — "Which item did you mean?" — and
   the app shows the options.
8. The app loops until the restocker is done.

### STACK ###
- **Frontend:** React Native / Expo / TypeScript
- **Backend:** Node.js / TypeScript using Express or Fastify
- **External API:** Micromart REST endpoints
- **Auth for MVP:** hardcoded cookie/session via environment variables
- **User model for MVP:** single user, one active restock session

### CRITICAL ARCHITECTURE DECISIONS ###
- The mobile app **stays thin**.
- The mobile app talks **only to our backend**, never directly to Micromart.
- The backend owns Micromart auth, planogram fetching, command parsing, product
  resolution, restock event submission, validation, error handling, and logging.
- Abstract auth behind an **`AuthProvider`** so the hardcoded cookie can later be
  replaced with real username/password login and possibly 2FA.
- Keep Micromart-specific endpoints inside a **`MicromartClient`**.
- Keep product matching in a separate **`InventoryResolver`** (a "Command +
  Inventory Resolver Service").
- **Do NOT reduce the planogram to `{ name: siteId }`.** Keep a rich inventory
  model: `siteInventoryId`, display name, normalized name, aliases, recipe ID,
  cell position, and other useful fields.
- The resolver must support exact matches, aliases, contains/includes matches,
  fuzzy matching, ambiguous-match detection, and not-found responses.
- Add **audit logging** for attempted corrections.
- Handle errors for: expired auth, failed planogram fetch, invalid command,
  invalid quantity, product not found, ambiguous product, failed Micromart POST,
  and missing session.
